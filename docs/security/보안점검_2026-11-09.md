# glocare 보안점검 (2026-11-09)

범위: admin · abroad · caregiver · visa 앱 코드 + Supabase 마이그레이션(정책 최종상태 재구성) + 비밀키·헤더·의존성.
방식: 읽기 전용 코드 점검. 운영 DB·배포 사이트에는 접속하지 않음 → `보안점검_2026-11-09_확인쿼리.sql` 로 실제 상태 대조 필요.
표시: ✅ = 코드를 직접 열어 재확인 / (추정) = DB 실제 상태 확인 필요

## 공통 전제 (왜 위험이 커지는가)
- 4개 앱이 **하나의 auth.users** 를 쓴다. abroad 학생(구글 가입)·caregiver 고객(문자 가입)은 **인터넷의 누구나** 만들 수 있다.
- 따라서 "로그인한 사용자(authenticated)면 허용" = 사실상 "누구나 허용".
- 브라우저에 공개된 anon key + 자기 로그인 토큰이면 화면을 거치지 않고 DB(PostgREST)를 직접 호출할 수 있다. RLS가 유일한 방어선.

## 🟡 중간

- abroad `/auth/callback` open redirect(`next=@evil.com`), `safeNext` 의 `/\` 우회
- AI 비용 남용: abroad 번역(`translateStudentValueAction`), caregiver 이력서 생성(권한·횟수 제한 없음), admin 이력서 다듬기
- 스팸: abroad 상담폼 확인메일 무제한, caregiver 문자 OTP 대량발송(Supabase 기본 제한에만 의존) → CAPTCHA/rate limit
- admin 영업(sales) 계정이 정산 완료·시스템 설정·임의 문자 발송 가능 (`isGlocareStaff` 기준)
- 직원 판정 초기 일괄 시드(0013, 0034)로 센터·학생 계정이 직원으로 남아 있을 가능성 (Q4)
- 보안 헤더 없음(CSP, X-Frame-Options, HSTS, nosniff), `poweredByHeader` 켜짐 — 4개 앱 공통
- `xlsx@0.18.5` 취약 버전으로 센터 업로드 엑셀 파싱 → 0.20.3+ 또는 exceljs
- caregiver 이력서 `photo_url` → 서버 fetch(SSRF), 결제확정 동시호출 중복기록, `study_managed_students` 학생이 `org_id` 변경 가능
- 트리거용 SECURITY DEFINER 함수 search_path 미설정(0011)
